# CampusHub

Платформа самообслуживания университетского кампуса

CampusHub объединяет доступ к аккаунтам, операции банкомата, заказы товаров и работу торговых
автоматов. Текущая версия реализует бизнес-правила этих сервисов и проверяет их
с помощью исполняемых спецификаций на Gherkin.

## Возможности

- **Заказы:** сохранение товара и количества в PostgreSQL, публикация события
  нового заказа в Kafka и логирование события сервисом уведомлений.

- **Банкомат:** снятие доступных средств, отказ при недостаточном балансе или
  некорректной сумме без изменения баланса. Суммы задаются целыми числами;
  реальные деньги не используются.
- **Доступ к аккаунту:** блокировка после трёх неудачных попыток входа подряд.
  Успешный вход сбрасывает счётчик ошибок; заблокированный аккаунт отклоняет
  вход даже с правильным паролем.
- **Кофемашина:** приготовление капучино при достаточном запасе молока,
  списание количества по рецепту и сохранение запаса при отклонённом заказе.

Заказы сохраняются в PostgreSQL. Состояние банкомата, аккаунта и кофемашины
хранится в Python-объектах и не сохраняется между запусками. Компоненты
пока не связаны общей системой счетов, HTTP API или веб-интерфейсом. Модуль входа
моделирует правила блокировки: пароль хранится в памяти, это не готовая система
аутентификации для реального приложения.

## Подготовка окружения

Нужны Python 3.11 или новее и виртуальное окружение в `venv/`.
Команды выполняются из корня репозитория.

Создать и активировать окружение:

```bash
python -m venv venv
source venv/bin/activate
```

Установить пакет и инструменты разработки:

```bash
python -m pip install -e ".[dev]"
```

Если окружение создано без pip, для установки можно использовать
[uv](https://docs.astral.sh/uv/):

```bash
uv pip install --python venv/bin/python -e ".[dev]"
```

Затем подключить Git-хук:

```bash
pre-commit install
```

Установка с флагом `-e` позволяет тестам сразу использовать изменения в `src/`.
Для заказов используются SQLAlchemy, psycopg и kafka-python. Прямые зависимости
зафиксированы в `pyproject.toml`.

## Проверки поведения

Запустить все спецификации:

```bash
behave
```

Запустить сценарии одного компонента:

```bash
behave features/authentication.feature
```

Сценарии проверяют отклонённые и успешные операции, а также граничные значения
баланса, числа попыток входа и запаса молока. Каждый сценарий создаёт новые
объекты: база данных, сервер и общее состояние тестов не нужны.

Git-хук запускает все сценарии перед каждым коммитом, даже если изменилась только
документация. Падающий сценарий останавливает коммит. Та же проверка вручную:

```bash
pre-commit run --all-files
```

При коммите окружение `venv` должно быть активировано: хук использует
`python -m behave` из текущего окружения, в котором установлен CampusHub.
После клонирования репозитория хук нужно установить заново: Git не переносит
установленные хуки.

## Структура кода

```text
src/campushub/
  atm.py        Правила снятия средств и баланс
  auth.py       Попытки входа и блокировка аккаунта
  vending.py    Приготовление капучино и запас молока
  models.py     Модель заказа SQLAlchemy
  orders.py     Сохранение заказа и отправка события
  notifications.py  Чтение событий и логирование
features/
  *.feature     Спецификации поведения
  steps/        Python-шаги и проверки результатов
```

Бизнес-компоненты не зависят от behave. Шаги связывают сценарий с подготовкой
данных, вызовом публичной операции и проверкой результата и состояния.
Отказы банкомата и кофемашины выражены предметными исключениями; попытка входа
возвращает признак успеха. Неожиданные исключения приводят к падению сценария.

Дальнейшее развитие: связать заказы и остальные компоненты через общие операции со счетами,
затем предоставить доступ к ним через API. В текущей версии это ещё не реализовано.


## Заказы и уведомления

Поток обработки: `orders → PostgreSQL → Kafka → notifications → logging`.
Сервис заказов подтверждает транзакцию до публикации JSON-события с полями
`id` и `item_name` и ожидает подтверждения брокера. Идентификатор заказа
генерируется PostgreSQL. Количество должно быть положительным целым числом.

`create_order(order, session, producer, topic)` принимает несохранённый объект
`Order`, выделенную сессию SQLAlchemy и KafkaProducer. Producer должен принимать
байты: сериализацию JSON выполняет сервис. Подключения создаёт и закрывает
вызывающий код, адреса БД и брокера задаются при создании клиентов.

`consume_one_notification(consumer, timeout_seconds=15)` читает одно событие
через KafkaConsumer, подписанный на нужный топик, логгирует идентификатор и
название товара и возвращает событие. Для обработки потока функцию можно
вызывать в цикле. Логгер: `campushub.notifications`, уровень `INFO`.
Функция не подтверждает смещения; в интеграционной проверке автокоммит отключён.
Это логирование событий, без отправки email или push-уведомлений.

Запись в БД и публикация не являются общей атомарной транзакцией. При ошибке
Kafka функция поднимает исключение, а заказ остаётся сохранённым. Автоматическое
повторение вызова может создать второй заказ. Гарантированная доставка,
идемпотентность и transactional outbox пока не реализованы.

## Интеграционные проверки

Нужен установленный Docker с работающим daemon и доступом текущего пользователя
к нему. Проверить доступность:

```bash
docker info
```

После установки зависимостей разработки запустить:

```bash
pytest -m integration
```

Testcontainers автоматически запускает PostgreSQL `postgres:16.6-alpine`
и Apache Kafka `apache/kafka:3.9.1` в режиме KRaft.
Отдельно устанавливать PostgreSQL, Kafka или ZooKeeper не требуется.
Первый запуск загружает образы и требует доступа к реестру контейнеров.

Каждый тест получает новые контейнеры, БД, топик и consumer group.
Все заказы создаёт `OrderFactory` из factory-boy: несколько предварительных
записей сохраняются напрямую, а новый заказ проходит через сервис.
Проверка читает сохранённый заказ из новой сессии, сравнивает данные и число
записей, затем вызывает сервис уведомлений и проверяет событие и лог.
Чтение Kafka начинается с earliest и ограничено таймаутом. Отсутствие Docker
или сообщения приводит к ошибке теста. Подключения и контейнеры освобождаются
фикстурами при успешном завершении и при падении проверки.

Файлы проверок:

```text
tests/
  factories.py
  integration/
    conftest.py
    test_order_notifications.py
```

BDD-проверки по-прежнему запускаются командой `behave`. Pre-commit запускает
BDD-сценарии; интеграционные проверки с контейнерами выполняются отдельно.
